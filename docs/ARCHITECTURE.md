# Nexus Vault — архитектура

Рабочий документ. Описывает принятые решения; меняется вместе с кодом.

## 1. Общая схема

```
┌──────────────── WebView (React) ────────────────┐
│  UI, формы, навигация, состояние экрана          │
│  НЕТ: ключей, крипты, доступа к БД и ФС          │
└───────────────┬─────────────────────────────────┘
                │ Tauri IPC: только явные команды
┌───────────────▼──────────── Rust ───────────────┐
│ commands/  — тонкий слой IPC, валидация входа    │
│ core/      — сессия хранилища (Locked/Unlocked)  │
│ crypto/    — KDF, AEAD, envelope, генератор      │
│ database/  — SQLite, миграции, репозитории       │
│ backup/    — формат .nexus                       │
│ platform/  — трей, буфер обмена, автоблокировка  │
└───────────────┬─────────────────────────────────┘
                ▼
        %APPDATA%\<app-id>\vault.db (SQLite, WAL)
```

Граница доверия — IPC. Всё, что выше неё, считается потенциально скомпрометированным
(XSS в WebView), поэтому:

- Vault Key и KEK живут только в Rust, в обёртках `zeroize`/`secrecy`.
- Пароль записи по умолчанию в JS не отдаётся: копирование делает Rust по `item_id`
  (`copy_field(item_id, "password")`). В JS пароль попадает только по явному «Показать».
- Мастер-пароль передаётся одной командой (`unlock` / `create_vault`) и сразу
  затирается в Rust; на фронте поле очищается после отправки.
- Tauri capabilities: без `fs`, `shell`, `http`. Плагины — только нужные
  (clipboard, dialog для выбора файла бэкапа, autostart, global-shortcut, notification,
  single-instance). CSP строгая, без внешних источников.

## 2. Криптография

Только проверенные крейты: `argon2`, `chacha20poly1305` (XChaCha20-Poly1305),
`rand`/`getrandom` (OS CSPRNG), `zeroize`, `secrecy`.

```
master password ──Argon2id(salt, params)──► KEK (32 B)
KEK ──XChaCha20-Poly1305──► расшифровка envelope ──► Vault Key (32 B, случайный)
Vault Key ──XChaCha20-Poly1305──► payload каждой записи / папки / тега
```

- Salt (16+ B) и параметры Argon2id (m, t, p) хранятся в `vault_meta`, поэтому их можно
  усиливать без потери старых хранилищ. Стартовые параметры подбираются бенчмарком
  на целевой машине (ориентир 0.5–1 с на разблокировку, память ≥ 64 MiB).
- Nonce — 24 случайных байта на каждое шифрование. Для XChaCha это безопасно и не требует
  счётчиков.
- AAD (связанные данные) = `vault_id ‖ item_id ‖ item_type ‖ crypto_version`.
  Нельзя подменить или переставить шифротексты между записями — расшифровка упадёт.
- Смена мастер-пароля = перешифровка только envelope Vault Key (записи не трогаются).
- `crypto_version` в каждой строке → поддержка старых форматов при обновлениях.
- Неверный пароль определяется ошибкой аутентификации envelope; отдельного хеша пароля
  в базе нет.

## 3. База данных

`rusqlite` с вшитым SQLite (`bundled`): синхронный, предсказуемый, нормальные транзакции.
Доступ через один `Mutex<Connection>` в состоянии приложения — для локального
однопользовательского приложения этого достаточно.

Миграции — SQL-файлы в `src-tauri/migrations/`, вшиваются в бинарник, применяются
по порядку в транзакции, учёт в `schema_migrations`.

Что лежит в открытом виде (и почему):

| Поле                                        | Открыто | Причина                                                                      |
| ------------------------------------------- | ------- | ---------------------------------------------------------------------------- |
| `id`                                        | да      | случайный UUIDv4, ничего не говорит о содержимом                             |
| `item_type`                                 | да      | фильтры по разделам без расшифровки; раскрывает только число паролей/заметок |
| `folder_id`, `is_favorite`, даты            | да      | сортировка и разделы; не раскрывают содержимого                              |
| название, URL, логин, пароль, заметки, теги | **нет** | только в зашифрованном payload                                               |
| имена папок и тегов                         | **нет** | шифруются тем же Vault Key                                                   |

Теги хранятся внутри payload записи (как в ТЗ), таблица `tags` — зашифрованный справочник
имён. Таблица `item_tags` не используется, чтобы не раскрывать связи — будет решено
окончательно в Phase 4.

## 4. Поиск

FTS по открытому тексту запрещён. При разблокировке Rust расшифровывает «сводки»
записей (название, сайт, логин, теги) в память, поиск идёт по ним в Rust.
10 000 записей — это единицы мегабайт и миллисекунды на поиск. При блокировке индекс
затирается.

## 5. Блокировка

`core::Session` — `enum { Locked, Unlocked(UnlockedVault) }`. Lock:

1. Vault Key, индекс и кеши затираются (`zeroize` при `Drop`).
2. Rust шлёт событие `vault-locked`, фронт сбрасывает сторы, закрывает диалоги
   и уходит на Unlock Screen.
3. Таймер очистки буфера обмена срабатывает досрочно, если в буфере ещё наш секрет.

Ограничение честно фиксируем: JS-строки не затираются гарантированно, а ОС может
сбросить память в своп. Мы минимизируем время жизни секретов, а не обещаем
защиту от форензики.

## 6. Фронтенд

- React 19 + TypeScript + Vite, Tailwind CSS v4, shadcn/ui (Radix), Lucide.
- Роутинг: React Router. Состояние: Zustand (без `persist` для любых данных хранилища).
- Формы: React Hook Form + Zod; те же ограничения повторно проверяются в Rust.
- Весь доступ к Rust — через `src/services/*` (типизированные обёртки над `invoke`).
  Компоненты `invoke` напрямую не вызывают.
- Тема и другие несекретные настройки хранятся в таблице `settings`.

## 7. Тесты

- Rust unit: crypto (неверный пароль, порча шифротекста, чужой ключ, уникальность nonce,
  смена пароля), миграции, репозитории.
- Rust integration: создание → разблокировка → CRUD → блокировка на временной БД;
  проверка, что в файле БД нет открытого текста.
- Vitest + RTL: компоненты, сторы, генератор (UI-часть).
- Playwright: e2e основных сценариев по фронту (с моками IPC).

## 8. Сборка и CI

npm + `package-lock.json`, `Cargo.lock` в репозитории. GitHub Actions на `windows-latest`:
lint, typecheck, Vitest, `cargo clippy`, `cargo test`, сборка установщика (NSIS).
